# Ghost Trade Identification & Resolution Architecture

## 1. The Sierra Chart Server Desync (The "Delayed/Missing" Trades)

When reviewing Sierra Chart logs, it is critical to distinguish between when an order is **submitted** and when it is **filled**. Furthermore, in Simulation mode, SC can experience server-client disconnections that lead to rolled-back transactions.

In the screenshots for the `02:26` entry on `2025-12-18`:
1.  **Submission**: At `02:26:26`, the strategy submitted **1 Market Order** (the entry) and **4 Limit/Stop Orders** (the targets/stops). The chart draws an arrow at 02:26 for all 5 orders because that is when they were placed.
2.  **Simulation Execution**: The logs show `ActivityType: Orders` with a status of `Filled` at `03:05`, `03:23`, and `03:43` as the price moved. These were *virtual* updates generated by SC's local client.
3.  **Server Rollback**: At `04:05:48`, SC realized it never actually received execution confirmation from the server. SC explicitly logs: `Orders | Canceled | Internally marking as canceled. No order update from server.`
4.  **Position Desync**: Because those 3 simulated targets were rolled back, Sierra Chart states: `Updates Service Position Quantity to -2`.
5.  **Forced "Ghost" Injection**: To forcibly match its local DB to the remote server, SC calls the "Trading Evaluator" at `04:05:56`. It injects a hard `ActivityType: Fills` record for `Market 2` to resynchronize the position.

**Conclusion:** The trades at 03:05, 03:23, and 03:43 **did fail**. They were canceled internally by SC due to a server desynchronization. In the **Trade Activity Log (TAL)** they appear as **Activity Type: Orders** (not **Fills**); only the 02:26 entry and the real 04:18 exit are **Activity Type: Fills**.

## 2. Defining a "Ghost" Trade

A "Ghost Fill" is a forced execution injected directly into the log by Sierra Chart's internal "Trading Evaluator" system to re-synchronize a broken simulation. They mathematically corrupt sequential Trade pairing.

**A fill is definitively a GHOST if it meets ALL of the following criteria:**

1.  **Format:** It exists in the `TradeActivityLogs` binary data as a real `Fill` record (Tag 102 / 0x66).
2.  **Missing Identifier:** Its corresponding Tag 0x82 / 130 (The "Note" field) is completely empty or missing. 
    *   *Note: Valid strategy trades always have a populated 0x82 tag, such as `AT_NQ_TM(D-R-2+last50)` or standard User notes.*
3.  **Not EOD Liquidation**: It occurs outside the final End-Of-Day liquidation window (typically 16:55 to 17:01 NY time). EOD liquidations validly lack Tag 0x82 and must be preserved.

*Why IsAutomated fails:* The Text Export (`ALLTradeActivityLogExport`) marks these ghost fills as `IsAutomated: Y`, identical to real strategy trades. There is no silver bullet column. We strictly rely on the missing 0x82 tag in the binary log combined with the time restriction.

## 3. The Global Bulletproof Solution (Pre-FIFO Dropping)

We have moved to a **Pre-FIFO Blocking** strategy within the `BinaryLogParser`. This ensures that ghost fills never enter the matching engine, preventing mathematical position corruption at the source.

### A. Pre-Filter Implementation
1.  **Binary Extraction**: The Nitro parser extracts raw `Fills` from the `.data` file.
2.  **Adaptive Threshold (NEW)**: Before applying any filters, the parser calculates the **Note-Rate** for the entire file.
    -   **Bypass Logic**: If **< 25%** of fills have a populated Tag 0x82 Note, the account is detected as a **"No-Note Setup"** (common in accounts like `TM_2` or `TM_10`).
    -   In this case, the Ghost Filter is **disabled** to prevent legitimate trades from being dropped.
3.  **Active Filtering**: For high-note-rate accounts (like `V_SIM16`), any fill with an empty Tag 0x82 Note (outside the 16:55-17:05 NY window) is **Dropped** immediately.

### B. Fills vs Orders in the binary
The SC binary log does **not** expose an "Activity Type" (Fills vs Orders). The parser identifies fill-like records by message text (e.g. "Trade simulation fill"). Records at 03:05, 03:23, and 03:43 are **Orders** in the TAL but carry the same message, so they can be imported as fills unless filtered.

**Current filters (all cross-account / cross-symbol):**
-   **Order-type at flush**: Records with Tag 107 containing **"stop"** are never emitted (03:05 Order blocked). Records with Tag 107 **"limit"** and message that does **not** contain "trading evaluator" are dropped (03:23, 03:43 Order records).
-   **Ghost detection (post-parse)**: Fills with no Tag 0x82 Note and no "Text: Tag" / "Tag: AT_" in the message are marked `suggests_ghost` and dropped before FIFO. Exception: plain "Trade simulation fill" + Tag 107 **Market** (no "trading evaluator" in msg) = true Fill; "Trading Evaluator (Filled)..." with "Text: Tag" in message = real fill (04:18 exit). A safety pass ensures any fill with "trading evaluator" in msg but no note and no "text: tag" is forced to `suggests_ghost`.
-   **Canceled order IDs**: We collect order IDs from "Internally marking as canceled" and drop fills with that order_id; in practice, order_id is often not set on these records in the binary, so this does not always apply.

Result: 03:05 (Stop Limit) and 03:23/03:43 (Limit, plain message) **Order** records are not imported. The 04:05 ghost (no note) is dropped via `suggests_ghost`. Real 02:26 and 04:18 Fills are kept. FIFO pairing is correct modulo other open positions in the same file.

### C. Result for 12/18 (V_SIM16)
-   The ghost at 09:05:56 UTC (04:05 NY) is **Blocked** (no note → `suggests_ghost`).
-   The 03:05 **Order** (Stop Limit) is **Blocked** at flush (Tag 107 "stop").
-   The 03:23 and 03:43 **Order** records (Limit, plain "Trade simulation fill") are **Blocked** at flush.
-   The real BUY 3 (02:26) and SELL 3 (04:18) are imported.
-   **Binary import:** Pairing is FIFO only — 07:26 BUY may close an earlier SHORT, so entry 3 + exit 3 can mismatch.
-   **Text export import:** Use Trade Activity Log → File → Save Log As (ActivityType=Fills). Paste includes OpenClose — pairing matches SC exactly (entry 3 + exit 3).

## 4. Chart Scenario: Ghost Open (+2 at 04:05) and SC “Flipping” Trades
On the chart you have: **02:26** Long +3 @ 25039 (real entry), **04:05** +2 @ 25046.75 (ghost — SC injects this), **04:18** -3 @ 25030.75 (real exit). SC then thinks position is +5 (3+2). When the real -3 hits, SC can **flip or mis-pair** the order of trades (e.g. treating the -3 as closing the wrong legs). The pink arrows in between are signals only and were not executed.

**Correct outcome:** One long trade: entry 02:26 +3, exit 04:18 -3. The ghost +2 at 04:05 must not add to our position.

**Not:** We do **not** remove the real entry (02:26). We remove **only** the ghost leg(s). If we removed both the ghost and the 02:26 entry we would be left with an orphan -3 exit. The “clean” result is one long trade (02:26 → 04:18), not a short.

## 5. Remove Only the Ghost Leg(s), Then Re-Pair
When we remove a ghost, we remove **only that leg** (the ghost fill), never the real entry or exit. We then re-pair on the remaining fills.

**Ghost can be open or close:**
- **Ghost open** (e.g. 04:05 +2): SC injects a fake add to position. We skip adding it to the queue so position stays +3; the next real close (-3 at 04:18) pairs with the real open (02:26 +3).
- **Ghost close** (e.g. phantom -2): We skip that close so it does not consume from the queue; the real open stays in the queue and the next real close pairs with it.

**Implementation:**
- **Pre-pairing (default):** Ghost fills are dropped before FIFO, so neither ghost opens nor ghost closes enter the engine.
- **In-pairing (defer_ghost_removal):** When we see a fill with `suggests_ghost=True`, we skip it: if **open**, we do not add to buys/sells; if **close**, we do not consume from the queue. Real entry stays; next real close pairs with it.

## 6. Why Pre-FIFO is Better
Earlier "Post-FIFO" strategies attempted to let ghosts match and then delete the resulting "Tainted" trades. However, this caused position drift where entries matched with the wrong exits. By **dropping ghosts at the source** (or skipping ghost legs — open or close — in the pairing loop), we ensure the FIFO engine only ever sees real opens and real closes; the next real close pairs with the real open.

## 7. Sierra Chart Documentation: Identifying Problem Fills and Mismatches
Sierra Chart does not document “ghost” fills by name. These references help identify when fills can cause wrong trade lists and how SC behaves:

- **Trade Activity Log** ([sierrachart.com/doc/TradeActivityLog.php](https://www.sierrachart.com/index.php?page=doc/TradeActivityLog.php)): The Trades/Statistics tabs “have a 100% dependency on correct order fills. You need to be sure there are **no missing order fills, no duplicate fills**, and the **order fill prices and quantities are correct**.” So any duplicate or wrong-quantity fill can cause mismatches.
- **Filter Initial Fills Part of Existing Position**: Trade Activity Log → Edit → **Filter Initial Fills Part of Existing Position**. When the first loaded fill is “within an existing Position, that fill and subsequent fills will get filtered out until the order fill which starts a new Position is encountered.” So SC itself treats “fills that are part of an existing position” when they shouldn’t be as problematic — similar in spirit to our ghost open (a fill that wrongly adds to position).
- **Use Last In First Out Fill Matching**: Edit → **Use Last In First Out Fill Matching** — toggles FIFO vs LIFO; wrong matching method can reorder trades.
- **Trade Activity Log Analysis** ([sierrachart.com/doc/TradeActivityLogAnalysis.php](https://www.sierrachart.com/index.php?page=doc/TradeActivityLogAnalysis.php)): For support-assisted analysis, SC needs Internal Order ID, exact date/time and time zone, account, symbol, and Trade Activity Log files. We identify ghost fills in binary by **empty Tag 0x82 (Note)** plus time window (excluding EOD).

**How we identify the mismatching trades:** (1) In binary we mark as ghost any fill with empty Note (0x82) outside EOD. (2) We remove only that leg (open or close) and re-pair; the real entry stays, the next real close pairs with it. (3) That yields one clean long trade (02:26 → 04:18) instead of SC’s flipped/mis-paired list.

## 8. What Sierra Chart Says — and You’re Not the Only One

**SC does not document the binary format or provide a programmatic export.** On the Support Board ([Thread 100015](https://www.sierrachart.com/SupportBoard.php?ThreadID=100015) — “Problems In Directly Converting Trade Activity Log .data Files to CSV”): users asked for direct .data → CSV conversion or binary format documentation. SC replied they *could* add an ACSIL function for Trade Activity Log → text export. As of **Feb 2026** someone asked for an update; SC replied: *“There is no update about this. We do not have time to work on this now and we do not know when.”* So there is **no planned** official way to parse .data files or get ParentInternalOrderID in an export. Others are in the same situation and have to parse the binary themselves or use the manual “Save Log As” text export.

**Chart / Trade List mismatch (fills “off by one”).** On the Support Board ([Thread 90069](https://www.sierrachart.com/SupportBoard.php?ThreadID=90069) — “Order fills on chart off by one, not matching with trade activity log”): a user had the first trade of the day matched to the previous day’s close, with chart fills not matching the Trade Activity Log. **SC’s official fix** is to set the **Order Fills Start Date / Start Time** correctly (and the Trade Activity Log “From Date / From Time”) so the first loaded fill is the start of a new position. SC points to:
- [Chart Trading: Accurate Entry/Exit State, Fill Matching and Position Quantities](https://www.sierrachart.com/index.php?page=doc/ChartTrading.html#OrderFillsOnChart_AccurateEntryExitState_FillMatching_PositionQuantities)
- [Trade Activity Log: Understanding and Setting the Start Date-Time for a Trades List](https://www.sierrachart.com/index.php?page=doc/TradeActivityLog.php#UnderstandingAndSettingTheStartDateTimeForATradesList)

That fixes **in-UI** chart vs log alignment; it does **not** fix exporting from .data with exact pairing (ParentInternalOrderID is still not in the binary).

**Practical ways to “solve” it:**

| Approach | What it does | Limitation |
|----------|----------------|------------|
| **Binary-only import (our pipeline)** | Parse .data, drop ghosts, FIFO pair. | ~24% trade-level match to SC Trade List; fill-level ~99%. No ParentInternalOrderID in binary. |
| **Use SC “Save Log As” (Trade Activity tab)** | Export Activity or Trades as text; that export can include OpenClose / ParentInternalOrderID. | Manual step; not automated from .data. |
| **Reference-derived pairing** | Use SC Trade List + Activity text exports to infer (entry_oid, exit_oid) pairs, then map to binary fills. | Needs reference files; we get ~90%+ trade match in benchmarks. |
| **Ask SC for binary format or ACSIL export** | Request documented .data format or an ACSIL “export to text” function. | SC has said no timeline; others have already asked (Thread 100015). |
